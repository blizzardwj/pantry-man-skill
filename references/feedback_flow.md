# Feedback Flow — 个性化信号的捕获与复用

本文件落实 [SKILL.md](../SKILL.md) 的反馈边界；数据字段见 [schema.md](schema.md)。以下数据路径均相对于 `[AGENT_HOME]/pantry/data/`。库存、清单和购买历史分别以 `pantry.json`、`shopping.json` 和 `history/YYYY-MM.json` 为准；`feedback.json` 保存可用于后续个性化的信号，不记录普通 CRUD 的执行进度。用户规则只写 `profile.json`，不改技能文件。

## ① Capture：先区分业务操作与反馈

一条消息可以同时包含两者，逐个意思处理。**判断标准**：这句话是否提供了以后选品或搭配可复用的个人信息？普通库存数量变化和一次性清单操作本身不满足这个标准。“吃完了”是例外：它既改变库存，也提供“买来并消耗过，日后可能需要补”的信号；这仍不等于长期喜爱或下次必须买。

| 用户表达 | 立即更新的业务数据 | 属于 feedback？边界判断 | 反馈记录与后续用途 |
|---|---|---|---|
| “买了苹果”／“今天买了 2 个苹果” | 当前购买：更新 `pantry.json`，对应待购项默认标已购，在 `history/YYYY-MM.json` 记购买 | 否：购买只证明入库，不证明喜欢 | 不新增；若有旧苹果耗尽信号，只将旧信号置 `decayed` |
| “家里还有 2 个苹果”／“补了苹果” | 更新 `pantry.json`；“已有”不生成购买历史，也不自动勾选待购项 | 否：只是当前库存事实 | 不新增；当前有货时结束被取代的旧耗尽信号 |
| “苹果吃完了”／“苹果用完了” | 删除或清零陈述覆盖的 `pantry.json` 库存 | 是：明确消费过，提供日后可能复购的线索 | 按食材记一条 `stock-change`、`stockEvent=depleted`、`status=active`，供以后采购计划选择性参考 |
| “苹果坏了／扔了”／“把苹果从库存删掉” | 按表达更新 `pantry.json` | 否：没有消费证据 | 不新增补购信号 |
| “把牛奶加进／从清单删掉”／“这次不买” | 更新 `shopping.json` 或本次采购提案 | 否：只说明本次清单操作 | 不新增；不推断长期讨厌 |
| “你把苹果数量记错了，实际还有 2 个” | 纠正 `pantry.json`，按当前有货处理旧耗尽信号 | 否：一次库存纠错不提供可复用偏好 | 不新增 |
| “以后别推荐牛奶”／“我更喜欢鲷鱼” | 更新 `profile.json` 的明确偏好 | 是：明确表达以后适用的偏好 | 记录 `preference-correction`，供以后选品和搭配使用 |
| “这道搭配太油”／“以后做法尽量简单” | 修正本次输出；长期要求明确时更新 `profile.json` | 是：评价已有搭配或提出未来规则 | 记录 `pairing-feedback` 或明确的偏好／规则，供以后生成使用 |
| “买了苹果，以后早餐多安排苹果” | 前半句按当前购买处理；后半句更新 `profile.json` | 部分是：只有后半句表达未来偏好 | 只记录后半句；不从购买本身推断偏好 |

执行步骤：

1. 读本次涉及的业务文件及 [schema.md](schema.md)。按 `itemKey` 关联同一食材；先落实用户说清楚的 CRUD，不因反馈重要性低而延迟操作。更新实际改动文件的 `meta.lastUpdated`；购买历史的统计按现有记录重算。
2. 只有边界列标为“是”或“部分是”的相应内容进入 `feedback.json`。消耗信号一食材一条；同句话包含多种食材时各用相同 `source`，分别记录 `itemKey`。明确偏好或评价按其作用范围记录，不把一次性删改写成长期偏好。
3. “吃完了”的信号取当前观察时间作 `effectiveAt`；历史补述若时间不明，保留未知，不据此覆盖后来的库存。只有明确消费或用完才建立消耗信号；库存不存在时不造负数量，仍可记录用户明确报告的消费。
4. 当前买回或确认已有某食材时，只将被这次有货事实取代的该食材旧 `depleted` 记录置 `decayed`。加进清单、本次不买、清单删除、单纯过期或时间流逝都不使它失效。补货后再次吃完，建立新的 `active` 消耗信号。
5. 食材、剩余数量或历史先后不清时，只执行能确定的部分；歧义会造成错误修改才针对它澄清。寒暄、系统提问及未回答不形成反馈。

<a id="purchase-steps"></a>
## ② 购买与普通 CRUD

1. 当前购买：读 `pantry.json`、`shopping.json`、`feedback.json` 和相应月份的购买历史。逐食材按实际已知数量更新库存；已有量或新增量未知时用 schema 的未知数量表示，不把清单计划量当作实买量。对应的旧耗尽信号按上节结束。
2. 若用户说“买了苹果”／“苹果买好了”，将匹配的 unchecked 待购项默认设为 `checked=true`；不要求实买量与计划量相同。明确“只买了一部分”或“还要再买”时保留待购，只在剩余量已知时调整需求。没有匹配项不创建已购清单项。
3. 当前购买未给其他日期时，按本地当天日期写 `history/YYYY-MM.json`；明确过去某日购买则用该日期。日期不清的历史补记不写到今天，若需要购买历史则询问日期。金额、价格和数量未知时按 schema 省略，不能编造。每次实际购买只记一笔，按 `records` 重算 `stats`。
4. 明确是在补记过去的购买时，只写有依据的历史；不凭这笔旧购买本身更新当前库存、勾选当前清单或结束后来发生的耗尽信号。若同句话另说“现在还在家里”，按这条当前库存事实更新。普通库存增删和清单 CRUD 直接改相应业务文件，不新增反馈记录。

**画像、规则和搭配：** 明确偏好写 `profile.preferences`／`cookingStyle`／`notes`，结构模板写 `pairingTemplates`，用户确认过的具体菜写 `exemplars`，用户级流程规则写 `rules`。待确认的 agent 推论不写成已确认偏好。同结构的 confirmed 范例 ≥3 道时可提议升模板，用户确认后才写；不改 SKILL.md。范例 > 模板 > 画像 > 通用的引用顺序继续适用，健康约束和明确偏好优先。

## ③ Threshold：整理真正的反馈

仅新捕获的消耗、偏好和搭配反馈参与原有阈值：当日 importance 累积 ≥8，或同实体／同类型 ≥3 条时，在当前自然执行点检查，不依赖后台进程。普通购买、库存 CRUD 和清单修改既不计数，也不因重复出现而自动变成偏好。

- merge 只合并同一事实的重复记录；不同食材或跨补货周期的两次耗尽不合并，保留原话并以 `mergedInto` 指向保留项。
- 多次买入或消耗同一食材可作选品线索，但不能自动推断“最喜欢”“每次都要买”。长期偏好需要用户明确表达或确认 agent 的推论。
- 明确的新事实取代旧事实时标 `decayed`。没有参考价值的旧记录可标 `evicted`，常规整理不删除原记录；importance ≥4 不仅因时间过去就淘汰。

## ④ Review：生成计划前消费信号

1. 每次生成采购计划或每日搭配前读 `feedback.json`、`profile.json`、`pantry.json` 和 `shopping.json`，不限当天有无新反馈。旧记录中的写入进度字段不是待执行任务。
2. 对 `active`、无 `mergedInto`、`stockEvent=depleted` 的记录，按 `itemKey` 核对当前库存和后续明确补货。已被有货事实取代的逐项标 `decayed`；先后无法确定时不据此认定缺货。
3. **采购计划**：有效消耗信号是候选线索，结合画像、库存、已有 unchecked 清单、本次饭菜目标与数量选择；不全部必推，不自动写购物清单。选中时可标“上次已吃完，可补”。本次提案刚删的项不自动加回。
4. **每日搭配**：只使用当前已确认购物条目和库存，不把耗尽候选或 `confirmation.proposedItems` 当成食材池；按明确偏好、范例、模板和规则生成。

<a id="confirmation-flow"></a>
## ⑤ 采购确认：先删改，再补问一次

`shopping.json.confirmation` 保存当前／最近一份采购提案；`proposedItems` 不是已确认购物条目。字段见 schema。

1. 展示新采购建议时创建 `confirmation.id`、`status=open`、`proposedItems` 和 `removedItemKeys=[]`。继续调整同一份建议沿用其 ID；确实开始新计划时才替换。
2. 用户删改立即更新本次 `proposedItems`。单纯删除的不同 `itemKey` 加入 `removedItemKeys` 并去重；改数量或替换不计删除。明确重新加入可移出该集合。已在正式清单中的直接删除照常执行，但不计入本提案的补问阈值。
3. 本轮删 ≥3 个不同条目且原因仍不清楚时，在执行删改后围绕最有帮助的未知信息问一次；本轮已经问过或用户已说明原因就不再问。未回答不猜测、不阻塞确认、不跨计划追问。提问本身和沉默都不是反馈。
4. 用户回答“已有／买了”按第①、②节更新业务数据并结束对应旧耗尽信号；“这次不买”只维持本次删除；明确长期偏好才进入反馈。可以这样问：“菠菜、芹菜、生菜这几样是家里已有，还是这次不打算买？也可以分别说明。”
5. 用户确认时，把获准的 `proposedItems` 按 `itemKey` 去重并入 `categories.food.items`，从提案移除这些项；全部确认则置 `status=confirmed`，部分确认则其余仍 `open`，取消则置 `cancelled`。只改用户明确获准的范围。若同句既删 ≥3 项又确认，先落实删改和清单，再在本次回执中问一次。新计划不继承旧 `removedItemKeys` 或未回答的问题。

<a id="legacy-feedback"></a>
## 已有反馈文件

`feedback.meta.version = "2.0"` 的现有文件继续读取和保存，不批量改写历史。旧记录可能含 `landings[]`、`applied`、`supersededBy`、`stockEvent=available/purchased`、`ingredient-fact` 或一次性操作记录；保留这些历史字段，但不执行旧 `landings[]`，也不把普通购买／库存变更当成偏好。旧 `depleted` 记录仍可用于选择性补购，明确补货后按新规则结束。新反馈记录不写操作进度字段。

遇到更早的非 v2 反馈文件，将其原样移至同目录唯一命名的 `feedback.legacy-<timestamp>.json`（文件名安全时间戳 YYYYMMDDTHHMMSS，重名加后缀），再创建 schema 的空 v2 文件；保留其他业务数据。归档失败就保留原文件，不覆盖，并说明具体失败。归档文件不参与 Review。
