# DECISIONS — 决策与有效性记录

> 本文件回答“最终选择什么、为什么、接受什么后果、后来是否被替代”，是**决策有效性的唯一维护位置**。
> 问题和实施进展见 [IDEAS.md](IDEAS.md)，研究过程见 [RESEARCH.md](RESEARCH.md)。本文件保留当时选择，不复制当前执行规范；当前行为见 [SKILL.md](../SKILL.md) 及 references。

### 记录约定

- 每项使用永久编号 `DEC-NNN` 和显式锚点 `dec-nnn`。本次按现有历史顺序由旧至新补号，新项取最大值加一；展示维持最新决策在前，同日保留既有相对顺序。
- 决策状态：`proposed`（待决定）、`accepted`（已接受）、`superseded`（整体被后项替代，必须链接替代项）、`deprecated`（不再适用且无直接替代）。accepted 不表示实现或验证完成；实施进展只链接 IDEAS。
- 一项只部分被替代时保留 accepted，在“适用范围／后续关系”明确被替代的部分；不得把“部分修订”误写为整项失效。新旧条目双向链接。
- 接受后的决策正文保留当时语义；重大改变写新决策，旧项补关系及日期。不把旧理由重写成“从一开始就这样”。当前状态和关系可更新，重要转折在条目末尾正序追加。
- 历史日期沿用原记录；本次补录时间独立标明。旧正文中“待实施／implemented／PASS”等是当时记录，不是另一处当前状态或本次验证证据。
- 新决策必须写背景、选择、理由、被否决的替代方案、后果（收益与代价），并关联想法／研究或直接提出该决策的证据。历史缺失字段只做明确标识的回顾归纳，不捏造当时讨论。

## [2026-10-12] 照片输入：小票即购买报告直接记录，识别类照片先确认

- 编号：DEC-030
- 决策状态：accepted
- 更新：2026-10-12
- 关联：[IDEA-033](IDEAS.md#idea-033)；[待办 A-04](improvement-todo-2026-10-11.md#a-04)；直接依据是用户确认支持小票、食材、冰箱三类照片并选择“小票直接记，识别类先确认”。
- 适用范围／后续关系：补充 [DEC-029](#dec-029) 的基本规则 1（“只依据用户所说改数据”）：小票照片视同用户陈述，其他照片不视同。补充 [DEC-024](#dec-024) 的“过期不等于消失”为同类原则：照片中看不到不等于没有。
- 背景：README 推荐语音与拍照输入的个人助理宿主，但契约未定义照片的含义。小票是印刷事实，食材或冰箱照片是 agent 的识别推断；冰箱照片还可能被当作完整盘点，把未拍到的条目删除。
- 决策：小票或订单截图按“买了”处理——物品视为已在家、匹配清单项勾选（用户另有说明除外），历史用小票上的日期、数量、价格与商店，名称取日常叫法；记录后回报明细供纠正。食材、冰箱或储物柜照片的识别结果是 agent 的推断，即使用户要求“按照片更新”也先列出（数量标为估计）并请求确认，只写入确认的部分；不因照片中看不到而删除或置 0。看不清的内容不猜。
- 理由：小票的商品、价格与日期是印刷事实，直接记录可补上此前常缺的价格数据，且回报明细保留纠错机会；视觉识别存在误认与数量估计，先确认符合基本规则 6（agent 的建议需确认）。
- 被否决的选项：
  - 一律先确认：小票也多一轮，降低拍照记账的价值。
  - 一律直接写入：识别错误直接进入库存，冰箱照片还可能导致误删。
  - 规则 1 改为“用户所说或清楚展示的”：执行中被理解为可直接写入清楚可见的识别结果（首轮冰箱用例 0/3），已弃用。
- 后果：收益是拍照可记账、可盘点而不误删。代价与局限：识别类照片多一轮确认；小票上的历史日期默认视为当前到家，补记很久以前的小票需用户说明；测试图片为合成图，真实照片识别效果待交互测试。
- 实施与验证入口：[IDEA-033](IDEAS.md#idea-033)。

## [2026-10-11] 库存过期状态读取时计算，不再存储 `status`

- 编号：DEC-027
- 决策状态：accepted
- 更新：2026-10-11
- 关联：[IDEA-029](IDEAS.md#idea-029)；[待办 F-06](improvement-todo-2026-10-11.md#f-06)。
- 适用范围／后续关系：替代 schema.md 原库存条目 `status`（fresh / expiring_soon / expired）的存储约定（来自早期提交，无对应 DEC 条目）；与 [DEC-024](#dec-024) 否决“自动写 status=expired”的理由一致。只涉及 pantry 条目，不涉及 feedback 记录与采购提案的同名 `status` 字段。
- 背景：`status` 可完全由 `expires` 和当天日期推出，但被作为字段存储；没有任何流程负责随日期更新它，存储值必然过时，并可能与 `expires` 矛盾（如已过期仍标 fresh）。
- 决策：过期状态每次展示或使用时按 `expires` 与本地当天日期计算：早于今天为已过期，今天至未来 N 天（默认 3）为即将过期，其余及无 `expires` 的条目不标状态。新写入不再存 `status`；旧文件中的 `status` 保留但忽略，不据此判断、也不回写更新。schema 将其标为 legacy。
- 理由：单一事实来源（`expires`）消除两字段不一致；无需后台进程或定期任务维护派生值，符合 agent 无常驻进程的约束。
- 被否决的选项：
  - 保留存储并在每次读取时回写更新：读取产生写入，与 [DEC-026](#dec-026) 只读无副作用冲突，且仍可能在两次读取之间过时。
  - 定期任务批量更新：依赖宿主定时能力，未启用时照样过时。
  - 删除旧文件中的 `status`：需批量改写用户数据；忽略即可兼容，无需迁移。
- 后果：收益是展示与过期检查始终与日期一致，过期判断不再受旧数据影响。代价与局限：agent 每次需按当天日期计算，依赖其正确获取本地日期；旧文件中的过时 `status` 仍留在数据里，读取者须遵守“忽略”规则。默认 3 天与定时提醒的“3 天内过期”一致。
- 实施与验证入口：[IDEA-029](IDEAS.md#idea-029)。

- 编号：DEC-026
- 决策状态：accepted
- 更新：2026-10-11
- 关联：[IDEA-028](IDEAS.md#idea-028)；[待办 F-05](improvement-todo-2026-10-11.md#f-05)。
- 适用范围／后续关系：部分替代 [DEC-001](#dec-001) 的初始化时机（“任何操作前检查并创建”）；DEC-001 避免首次报错、不覆盖已有数据的目标继续有效。不改变种子结构与旧反馈文件的处理规则。 2026-10-11 起 [DEC-029](#dec-029) 取消 feedback.json，首次写入时不再创建其种子；只读不建文件的规则不变。
- 背景：原 description 把“食材咨询”等宽泛场景列为触发条件，一般烹饪提问也可能加载本 skill；First-Run Setup 又要求任何请求前先建目录和种子文件，误触发或只读请求会在用户的 agent home 留下数据文件。
- 决策：只读请求（查看库存／清单／历史、过期检查、食材咨询）遇到缺失文件按空种子回答，不创建任何文件；首次写入（增删改、记录购买、记录反馈、保存计划或画像）前才执行初始化步骤，并把“已建好”与本次写入结果一并简短告知。食材咨询只在 profile.json 存在时读取，不创建。description 改为以用户自有库存、清单、购买和饮食画像为中心，明确排除与这些无关的一般菜谱／烹饪问题。

  - 在确认采购建议的一轮删改结束后，若删掉至少 3 个不同条目且原因尚不清楚，本次补问一个有助于调整计划的问题。先执行明确的删改，不等待原因才生效；不把改数量、替换食材或之后单独删已确认清单项自动计入本规则。

  - “这次不想买”仅维持本次删除，不改变库存、耗尽事实或长期偏好。未回答时也只执行已明确的删改，但原因仍是未知，不能记录成用户说了“不想买”。下一次仍按原有依据选择性推荐，同轮不加回刚删的项。
  - 提问本身不是用户反馈；删改不自动成为高重要性的长期结论。实际回答按内容判断类型、重要性及数据更新；明确“以后别推荐”等长期要求仍按偏好处理。
- 理由：当前删改已是清楚的操作指令，原因只影响后续如何改进。以真实回答修正信息，既能吸收有用反馈，也给用户不解释的空间。
- 被否决的选项：
  - 等用户回答原因才落实删除：阻塞已经明确的操作。
  - 未回答就推断不喜欢、已有库存或已购买：把未知原因写成事实。
  - 延迟到下次必问，或未回答持续追问：增加打扰和跨计划待办，违背本次问一次的选择。
  - “有了”一律生成购买历史：库存可能来自赠送或此前漏记，不能证明购买。
  - 删 ≥3 项或回答了系统的问题就一律 imp 4：事件数量和问题措辞不能决定回答是否有长期价值。
- 后果：无需为旧删除原因建立跨计划追问任务；未回答可能让库存或偏好继续不完整，这是保留用户选择空间的代价。实现仍须识别本轮是否已问过，防止中断恢复后重复问；不预先假定每次回答都有高价值。
- 实施与验证入口：[IDEA-018](IDEAS.md#idea-018)；具体例子与后续验收要求见 [RQ-5](RESEARCH.md#rq-5-clarification-once)。

  - 兼容旧 applied 并推断修复历史数据：当前开发版无需承担该成本，用户明确允许废弃旧语义。

### 历史决策正文

- 决策: 在 `references/ingredient_knowledge.md` 新增**跨类别**「膳食纤维速查」段——鲜品表（荷兰豆 6.8 → 叶菜 0.7–2.2 g/100 g）+ 干品/籽类表（菌藻、籽类、干豆、谷物、魔芋精粉）+ 两类纤维取向 + 摄入量与注意事项；并在段首**强制口径标注**（鲜重/干重、不溶性/总纤维、来源波动），数据来自《中国食物成分表（第 6 版）》/中国营养学会/USDA，附来源链接。
- 理由: 用户（开发者本人）实测提问"毛豆和豌豆纤维是否比蔬菜高"，暴露两个空白：①知识文件按食材类分组，只有"这一类怎么处理"，**没有跨类别横向比较**——而选品/答疑问题（谁更高、这次该多买哪类）本质需要排序；②网上同名食材数值互相矛盾（秋葵 1.8 vs 3.2 vs 3.9），根因是**没说口径**，速查表必须把口径写在表前，否则沉淀的知识反而误导。
- 被否决的选项:

- 理由: agent 无常驻进程——不存在"后台自己找活干"的守护进程，一切整理只能挂在宿主流程的自然执行点上（对话处理 / 日界 / 计划生成）；hooks 恰好同时编码"何时触发"与"挂在哪里"，比 triggers 多表达宿主-挂接关系。Layer 2 的阈值触发有文献出处：Generative Agents（Park 2023）重要性分数累积触发反思、MemGPT memory pressure 触发上下文整理
- 被否决的选项:
  - daemon（守护进程）—— 否决：agent 无常驻进程，无"主动监控"语义，时机由宿主决定而非自身
  - callback（回调）—— 否决：只覆盖即时触发（Layer 1），无法表达阈值批处理与消费时兜底
  - trigger policy / trigger points —— 否决：只表达"会触发"，不表达挂接位置与宿主关系，信息量不足
  - opportunistic reflection（机会式反思）—— 否决为术语，保留为语义注解：它准确描述了三层 hooks 的设计哲学（利用自然触点、不打扰用户），适合作为 hooks 的说明性描述而非正式命名

- 理由: 真实试用后痛点验证——记录/查询/提醒是录入负担，用户要的是"规划产出价值"。规划功能复用现有数据层（购物清单/购买记录/库存），不另起炉灶，价值密度远高于被动记录

- 画像形态: 可选 `profile.json`，不搞问卷；agent 对话中自然累积，首周规划后让用户二次确认/修正（二次确认优于一次问卷）
- 被否决的选项:
  - 做"画像问卷选择器"（家族基因/饮食文化/偏好一次性选择）—— 否决：首次使用变重，与 First-Run 轻体验原则冲突；且健康数据前置收集有隐私风险
  - 把"推荐食材"作为画像的落地场景 —— 否决：推荐准确性主要取决于模型知识而非粗分类画像，边际价值低；画像的正确场景是周规划
  - 另起独立 skill 做规划 —— 暂缓：闭环数据流（规划写回 shopping.json）在同一 skill 内实现最自然，独立 skill 留作未来拆分选项
- 风险与缓解: 涉及健康建议（糖尿病/冠心病史）→ SKILL.md 必须加入"非医疗建议，重大健康问题请咨询医生"免责声明
- 备注: 用户示例画像——中国人、父辈糖尿病+冠心病史、避免精制碳水/低GI碳水、少不健康油脂、加入心脑血管友好油脂、偏好蒸/煮/凉拌极简烹饪
